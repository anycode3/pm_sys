## 1 引言

### 1.1 背景

企业当前在项目推进、目标管理、绩效考核、经营决策支撑等方面使用多套割裂的管理方式,存在以下痛点:

1. **信息孤岛**:项目状态、目标达成、人员投入、考核指标分散在不同表格/系统中,无统一数据源;
2. **决策滞后**:决策层无法实时看到项目健康度与人员投入状态,风险发现依赖层层人工汇报;
3. **口径不一**:同一指标在不同场景下数值与口径不一致,对账成本高;
4. **投入不透明**:人员投入状态缺乏量化手段,超载与闲置并存,风险难以提前识别;
5. **目标与执行脱节**:战略目标拆解到项目与个人后,达成度无法自动回卷,目标管理流于形式。

为此,本项目拟建设一套**全新的一体化管理平台**,将**项目管理系统、OKR 系统、KPI 系统、顶层看板系统**四个子系统统一设计、统一数据底座,实现"数据打通、实时呈现、风险预警"。

### 1.2 文档目标

本文档是整个平台的**总体需求基线**,回答以下问题:

- 平台的定位、建设目标与成功标准;
- 四个子系统的职责边界与相互关系;
- 支撑"数据打通"的主数据与核心数据模型;
- 顶层看板与风险预警的概要需求;
- 各模块的概要功能边界与待澄清问题(供后续详细需求阶段使用);
- 非功能需求基线与阶段路线。

**本文档不包含**:各模块的功能点级详细需求、界面原型、数据库物理设计、技术选型。这些内容在后续阶段由独立文档承接。

### 1.3 适用读者

决策层(评审用)、产品/需求团队(后续细化用)、架构师、项目经理、研发团队。

### 1.4 术语与缩写

| 术语 | 说明 |
|------|------|
| 平台 | 本文档所述"项目·OKR·KPI·顶层看板一体化管理平台"的总称 |
| 目标树 | 平台的唯一目标事实骨架:公司级目标逐层拆解至板块/部门目标、再关联项目与关键结果 |
| OKR | Objective & Key Results,目标与关键结果,面向战略方向的对齐与推进机制 |
| KPI | Key Performance Indicator,关键绩效指标,面向岗位/业务的持续考核指标 |
| KR | Key Result,关键结果,OKR 中用于量化目标达成度的条目 |
| 指标字典 | 平台统一维护的指标定义(名称、口径、单位、周期、阈值),OKR 度量与 KPI 考核共用 |

## 2 总体描述

### 2.1 系统定位

**一句话定位**:以统一目标树为骨架、统一主数据为底座的项目/OKR/KPI 一体化管理平台,让决策层在顶层看板上实时看到项目状态、人员投入状态,并对项目、人员、目标指标三类风险提前预警。

### 2.2 建设目标与成功标准

| # | 目标 | 成功标准(概要) |
|---|------|----------------|
| 1 | 数据打通:四模块共享唯一事实源 | 同一指标/项目/人员在各模块中数值一致,无手工对账 |
| 2 | 实时看板:决策层一屏看全局 | 看板数据延迟 ≤ 5 分钟(待确认,见 8.1),一屏呈现战略+经营+项目+人员四视图 |
| 3 | 自动上卷:目标达成无需人工填报 | 任务/项目数据变更后,各级达成度自动重算 |
| 4 | 风险预警:从"事后知道"到"事前发现" | 三域(项目/人员/目标指标)风险规则可配置,预警自动产生并闭环处置 |
| 5 | 投入透明:人员投入可量化 | 人员投入由任务分摊自动汇算,超载/闲置可自动识别 |

### 2.3 用户与角色(通用定义,行业适配阶段细化)

| 角色 | 层级 | 核心诉求 | 主要使用模块 |
|------|------|----------|--------------|
| 决策层 | 集团/公司高管 | 一屏看全局:目标达成、经营健康、项目状态、人员投入、风险预警 | 顶层看板 |
| 管理层 | 板块/部门负责人 | 管理本级目标与下属项目,看团队负荷,处置预警 | OKR、项目(监督)、看板 |
| 项目主管 | 项目经理 | 项目计划、任务分派、进度管理、项目级汇报 | 项目管理 |
| 执行人员 | 一线员工 | 接收任务、填报进度,查看个人目标与考核 | 项目管理(任务)、OKR(个人) |
| 考核管理员 | HR/绩效岗 | 维护 KPI 考核方案与指标口径,查看考核结果 | KPI |
| 系统管理员 | IT | 组织、权限、指标字典、预警规则配置 | 全平台 |

> 待澄清:组织层级深度(集团->板块->部门->…共几级)、是否多法人主体、岗位体系,在行业适配阶段确认(见附录 A)。

### 2.4 总体约束与假设

| # | 类型 | 内容 |
|---|------|------|
| 1 | 假设 | 平台按**通用平台**设计,业务背景、行业术语通过"行业适配层"注入,不在核心模型中硬编码 |
| 2 | 假设 | 四模块**全新建设**,不存在遗留系统数据集成;但需预留与外部系统(财务、HR、OA 等)的接口扩展点 |
| 3 | 假设 | 人员投入数据**由任务分摊自动汇算**,不设工时填报流程 |
| 4 | 约束 | OKR/KPI 的关系采用"目标树骨架 + OKR 战略推动 + KPI 岗位考核"模型(见 4.3),该模型为本文档的数据模型基础 |
| 5 | 约束 | 风险预警范围限定三域:项目域、人员域、目标指标域;架构上预留扩展域 |
| 6 | 待确认 | 看板"实时"的具体口径(建议:事件驱动、分钟级,见 8.1) |

## 3 总体架构

### 3.1 逻辑架构(四层)

```
┌───────────────────────────────────────────────────────────────┐
│ 展示层 │ 顶层看板(决策层)+ 四模块工作台(各级用户)+ 预警中心    │
├───────────────────────────────────────────────────────────────┤
│ 计算层 │ 达成度上卷引擎 · 投入汇算引擎 · 风险规则引擎 · 指标计算  │
├───────────────────────────────────────────────────────────────┤
│ 主数据层 │ 组织 · 人员 · 目标树 · 指标字典 · 项目 · 任务 · 投入分摊 │
│ (唯一事实源,四模块共用 ——"数据打通"的本体)                        │
├───────────────────────────────────────────────────────────────┤
│ 采集层 │ OKR 制定录入 · KPI 数据录入/外部采集 · 项目任务填报 · 事件流│
└───────────────────────────────────────────────────────────────┘
```

分层职责:

- **采集层**:各模块的录入界面与外部数据接入,所有写入最终落为主数据层的实体/事实,并以事件形式发布(如"任务状态变更""KR 进展更新");
- **主数据层**:唯一事实源。四模块不各自建数据,全部引用主数据;这是消除信息孤岛与口径不一的根本手段;
- **计算层**:订阅事件,增量重算达成度、投入汇算、指标值,并按风险规则评估产生预警;
- **展示层**:面向角色的视图,顶层看板是其中面向决策层的聚合视图。

### 3.2 四模块职责边界

| 模块 | 职责(做什么) | 不做什么(边界) |
|------|----------------|------------------|
| 项目管理 | 项目立项(挂接目标)、计划与里程碑、任务分派与进度、项目文档与汇报 | 不定义目标与指标口径;不产生考核结论 |
| OKR | 目标的制定与拆解(沿目标树)、KR 制定与进展管理、对齐与复盘 | 不管理任务执行细节(任务归项目);不直接产生考核结果 |
| KPI | 指标字典维护、考核方案(指标×对象×目标值×周期)、数据采集与核算、考核结果 | 不定义战略目标;指标口径来自指标字典,不自建口径 |
| 顶层看板 | 四视图聚合呈现、逐层下钻、预警展示与处置跟踪 | 不录入业务数据(只读+处置动作);计算依赖计算层 |

### 3.3 关键设计原则

1. **单一事实源**:任何数据只有一个权威归属模块,其余模块只引用;
2. **事件驱动**:数据变更以事件发布,计算与看板订阅事件增量更新,支撑"实时";
3. **计算与展示分离**:看板不做业务计算,只呈现计算层结果,保证口径统一;
4. **配置优于编码**:指标口径、预警规则、组织层级尽量可配置,支撑通用平台+行业适配。

## 4 主数据与核心数据关系

### 4.1 主数据清单

| 主数据 | 权威归属 | 关键属性(概要) | 被引用方 |
|--------|----------|------------------|----------|
| 组织单元 | 系统管理 | 树形结构、层级类型(集团/板块/部门) | 全部模块 |
| 人员 | 系统管理 | 所属组织、岗位、角色 | 项目、OKR、KPI、看板 |
| 目标(Objective) | OKR | 层级、周期、权重、负责人、达成度 | OKR、项目、看板 |
| 关键结果(KR) | OKR | 度量指标、目标值、进展 | OKR、看板 |
| 指标(Metric) | KPI(指标字典) | 名称、口径、单位、周期、阈值 | OKR(KR 度量)、KPI(考核)、预警 |
| 考核方案 | KPI | 指标×考核对象×目标值×周期 | KPI、看板、预警 |
| 项目 | 项目管理 | 关联目标、负责人、计划、预算、健康度 | 项目、看板、预警 |
| 任务 | 项目管理 | 所属项目、责任人、权重、预估投入、截止、状态 | 项目、投入汇算、看板 |
| 投入分摊(事实) | 系统(自动) | 人×任务×时间×投入量 | 投入汇算、预警、看板 |

### 4.2 目标树(唯一事实骨架)

目标树是平台"数据打通"的骨架,OKR 与项目均挂接其上,**不各自建树**:

```
L1 公司级目标(年度/战略)
 ├── L2 板块/部门目标
 │     ├── L3 支撑项目(Project)──> 任务(Task)──> 人员投入
 │     └── L3 关键结果(KR)──> 引用指标字典中的指标
 └── ...
```

- 节点分层与组织层级对应(具体层级深度待行业适配确认);
- 每个节点记录:负责人、周期、权重、来源(由哪个上级目标拆解而来);
- **达成度上卷**:任务完成度 -> 项目进度 -> KR 达成 -> 目标达成,逐层按权重自动汇总;
- 一个项目可支撑多个目标(多对多),一个 KR 可由多个项目贡献。

### 4.3 四大核心实体关系(OKR/KPI 的打通模型)

采用已确认的模型:**目标树为事实骨架,OKR 驱动战略推进,KPI 作为岗位/业务稳定考核,看板双记分牌**。

```
目标树(骨架)
  Objective ──拆解──> 子 Objective
     ├─ KR(量化关键结果)──度量引用──> 指标字典 <──考核引用── KPI 考核方案
     │                                                    (指标×岗位/人员/组织)
     └─ 支撑项目 Project
          └─ 任务 Task ──分配──> 人员 Person ──岗位──> KPI 考核方案
                │
                └──> 投入分摊事实(人×任务×时间,自动汇算)
```

打通要点:

1. **指标字典是 OKR 与 KPI 的连接点**:KR 的度量与 KPI 的考核引用**同一指标实体**(统一名称、口径、单位、周期),从根上避免"两套账";
2. **人员双轨**:人员既有岗位 KPI(固定考核维度),又有 OKR/项目任务分摊(动态投入);两轨数据在看板与预警中分别呈现;
3. **项目是战略与执行的连接点**:项目上接目标(为什么做),下接任务与人(谁在做),是投入汇算与项目域预警的事实载体;
4. **达成度与考核解耦**:OKR 达成度用于目标管理与复盘(建议不直接挂钩薪酬),KPI 结果用于考核兑现;两者数据打通但用途分离。

> 待澄清:OKR 是否与绩效挂钩、考核周期(月/季/年)、KR 数量规范等,见附录 A。

### 4.4 核心数据流(打通机制)

六条关键数据流:

| # | 数据流 | 说明 |
|---|--------|------|
| F1 | 目标 -> 项目 | 目标树节点在制定/拆解时关联支撑项目;项目立项时必须挂接至少一个目标 |
| F2 | 项目 -> 任务 -> 人员 | 项目分解任务并分配责任人;任务含权重与预估投入,是投入分摊的来源 |
| F3 | 任务/KR 进展 -> 达成度上卷 | 任务状态或 KR 进展变更事件触发,逐层重算项目进度、KR 达成、目标达成 |
| F4 | 指标字典 -> KR/KPI/预警 | 指标定义变更通知引用方;指标值核算结果供 KR 度量、KPI 考核、指标域预警共用 |
| F5 | 投入分摊 -> 人员投入汇算 | 按人×时间×任务维度汇算投入,输出人员负荷(对比阈值产生人员域预警) |
| F6 | 三域事实 -> 风险规则引擎 -> 预警事件 -> 看板 | 规则引擎订阅各类事件与核算结果,产生分级预警,推送看板与责任人 |

## 5 顶层看板需求(概要)

### 5.1 定位与用户

面向决策层的全局聚合视图,只读为主(含预警处置动作),数据全部来自计算层,不产生业务数据。

### 5.2 双记分牌 + 四视图

| 视图 | 回答的问题 | 数据来源 |
|------|-----------|----------|
| 战略面(OKR 记分牌) | 战略目标推进得如何? | 目标树达成度、KR 进展 |
| 经营面(KPI 记分牌) | 日常经营稳不稳? | KPI 指标值 vs 目标值/阈值 |
| 项目面 | 哪些项目有危险? | 项目健康度(红/橙/黄/绿)、里程碑、预算执行 |
| 人员面 | 人用得对不对? | 人员投入/负荷分布、超载与闲置名单 |

- 全局统一**红/橙/黄/绿**健康度体系,贯穿四个视图;
- 看板首屏同时呈现**双记分牌**(战略达成 + 经营健康),这是本平台区别于普通项目看板的核心特征。

### 5.3 下钻路径

```
看板首屏
 -> 板块/部门(组织维度下钻)
    -> 项目(项目维度下钻:里程碑、任务、卡点)
    -> 目标/KR(目标维度下钻:进展、支撑项目)
    -> 人员(人员维度下钻:投入构成、负荷趋势)
 -> 预警列表(点击预警直达风险对象与规则详情)
```

下钻遵循"每一个数字都可追溯到源数据"原则(如某目标达成度可下钻到具体任务的完成记录)。

### 5.4 待澄清(详细需求阶段确认)

- 首屏具体指标卡构成与布局;
- 是否需要大屏投放模式(指挥中心场景);
- 汇报导出(周报/月报自动生成)是否纳入本期看板范围;
- 看板刷新方式与数据延迟指标(见 8.1)。

## 6 风险预警需求(概要)

### 6.1 三域预警框架

| 领域 | 预警信号(规则示例,阈值可配置) |
|------|--------------------------------|
| **项目域** | 里程碑逾期 / 逾期临近;进度偏差超阈值(实际 vs 计划);卡点(阻塞任务)停留超时;预算执行超支或偏差;项目健康度连续劣化 |
| **人员域** | 超负荷(投入汇算超上限阈值);长期闲置(投入低于下限阈值);关键人单点风险(一人同时支撑过多关键任务);投入与岗位/角色明显不匹配 |
| **目标指标域** | KR 长期无进展(停滞);目标达成偏差扩大(时间过半进度未过半类);KPI 连续 N 期恶化或触及红线;关联项目全部延期的目标 |

### 6.2 预警分级与生命周期

- **分级**:红(重大,需决策层介入)/ 橙(较重,管理层处置)/ 黄(提示,责任方自查);与全平台健康度色系一致;
- **生命周期**:`产生 -> 通知(看板+责任人) -> 认领 -> 处置 -> 复核 -> 关闭`;超时未认领自动升级;
- **留痕**:每条预警记录触发规则、触发时的数据快照、处置过程,支持事后复盘。

### 6.3 预警规则管理

- 规则 = 监控对象 + 指标/事件 + 阈值 + 级别 + 通知对象;
- 规则由系统管理员/授权角色配置,支持启停与版本管理;
- 初始规则集在详细需求阶段与业务方逐条确认(见附录 A)。

### 6.4 设计边界

- 预警只做**规则化识别**,本期不做基于模型的预测(如"预计延期 X 天")的承诺;架构预留接入预测模型的位置。

## 7 四模块需求概要卡

> 每张卡片含:定位、功能边界(概要)、主数据依赖、与其他模块关系、待澄清问题。详细需求由后续独立文档补充。

### 7.1 项目管理模块

- **定位**:任务执行与项目推进的事实载体,是投入分摊与项目域预警的数据源头。
- **功能边界(概要)**:项目立项(挂接目标、负责人、计划、预算)/ 里程碑管理 / 任务分解与分派(责任人、权重、预估投入、截止)/ 进度填报与状态流转 / 项目文档与汇报归档 / 项目健康度自动计算。
- **主数据依赖**:组织、人员、目标树(项目挂接)、指标字典(预算执行类指标)。
- **与其他模块关系**:向 OKR 提供支撑项目的进度(参与达成度上卷);向看板/预警提供项目状态与任务事实;任务分配产生投入分摊事实。
- **待澄清**:任务粒度规范、权重与预估投入的设定方式、项目类型差异(工程/研发/销售等)、是否需要审批流(立项/变更)。

### 7.2 OKR 模块

- **定位**:战略目标的制定、拆解与推进管理,沿目标树运作,是战略面记分牌的数据源头。
- **功能边界(概要)**:目标制定与逐层拆解(组织/个人维度)/ KR 制定与度量(KR 引用指标字典)/ KR 进展更新 / 对齐视图(上下级目标对齐检查)/ 复盘(周期结束时评分与复盘记录)。
- **主数据依赖**:目标树、指标字典、组织、人员。
- **与其他模块关系**:目标树节点关联项目(项目为 KR/目标提供进展);KR 度量与 KPI 共用指标字典;达成度上卷供看板呈现。
- **待澄清**:OKR 周期(建议季度)、是否覆盖个人 OKR、OKR 评分是否与绩效挂钩(建议不挂钩)、复盘流程深度。

### 7.3 KPI 模块

- **定位**:指标口径管理与岗位/业务持续考核,是经营面记分牌的数据源头。
- **功能边界(概要)**:指标字典维护(名称、口径、单位、周期、阈值)/ 考核方案配置(指标×考核对象×目标值×周期)/ 指标数据采集(手工录入 + 预留外部系统接口)/ 核算与结果(达成率、趋势)/ 考核结果查看与申诉流程。
- **主数据依赖**:指标字典、组织、人员、岗位。
- **与其他模块关系**:指标字典被 OKR 的 KR 引用(统一度量);来自项目/任务的事实(如准时率)可作为指标数据来源之一;指标值供预警引擎做指标域预警。
- **待澄清**:考核对象粒度(岗位/人员/组织)、考核周期、申诉流程是否本期建设、哪些指标可自动采集。

### 7.4 顶层看板模块

- **定位**:面向决策层的四视图聚合呈现与预警处置入口。
- **功能边界(概要)**:双记分牌 + 四视图首屏 / 逐层下钻(组织->项目/目标/人员)/ 预警列表与处置跟踪 / 数据追溯(每个数字可下钻到源)/ 自动汇报导出(待确认范围)。
- **主数据依赖**:全部主数据的计算层结果(只读)。
- **与其他模块关系**:不产生业务数据;预警处置动作回写预警生命周期(见 6.2)。
- **待澄清**:首屏指标卡构成、大屏模式、汇报导出范围、移动端是否需要。

## 8 非功能需求

### 8.1 实时性

| 项 | 指标(建议值,待确认) |
|----|------------------------|
| 数据延迟 | 业务数据变更到看板可感知 ≤ 5 分钟(事件驱动,目标为分钟级) |
| 看板刷新 | 支持自动刷新;刷新间隔可配置 |
| 预警延迟 | 规则触发到预警呈现 ≤ 5 分钟 |

### 8.2 性能与规模

- 看板首屏加载 ≤ 3 秒(常规网络);
- 下钻操作响应 ≤ 2 秒;
- 用户规模与并发:待行业适配阶段确认(架构按可横向扩展设计)。

### 8.3 安全与权限

- 基于角色的访问控制(RBAC),权限粒度覆盖:模块、组织范围(数据可见范围)、操作;
- 敏感数据(考核结果、人员投入明细)按角色与组织层级控制可见性;
- 关键操作(指标口径变更、预警规则变更、考核方案发布)留审计日志。

### 8.4 可扩展性与适配

- **行业适配层**:组织层级、岗位体系、指标模板、预警阈值模板、界面术语均可配置,不修改核心模型即可适配具体行业;
- **外部接口**:预留与财务、HR、OA 等外部系统的数据接入点(本期不实现,仅留扩展点);
- **扩展预警域**:风险规则引擎按"域"组织,新增预警域不改引擎。

## 9 阶段路线与后续澄清计划

### 9.1 建议阶段划分(概述,详细计划另行制定)

| 阶段 | 内容 | 产出 |
|------|------|------|
| S0 需求澄清(当前) | 本文档评审 + 各模块详细需求澄清 | 本文档定稿 + 四模块详细需求文档 |
| S1 数据底座 | 主数据模型详设:组织/人员/目标树/指标字典/事件机制 | 数据模型设计文档 |
| S2 项目管理模块 | 项目/任务/投入分摊建设 | 模块上线(支撑数据源头) |
| S3 OKR 与 KPI 模块 | 目标树运作、KR、指标字典、考核方案 | 两模块上线(补齐记分牌数据) |
| S4 顶层看板与预警 | 四视图看板、风险规则引擎 | 平台完整交付 |
| S5 行业适配与增强 | 行业适配层填充、汇报导出、移动端(视需要) | 适配交付 |

> 模块上线顺序的理由:项目/任务是事实源头,先有源头才能上卷与预警;OKR/KPI 补齐口径与记分牌;看板最后聚合呈现。

### 9.2 后续需求澄清计划

按模块顺序逐个开展详细需求澄清,建议顺序:项目管理 -> OKR -> KPI -> 顶层看板 -> 预警规则集(依赖前三者的口径确定)。
